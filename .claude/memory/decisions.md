# Decision record

Why the system is shaped the way it is. Entries marked **REVERSED** describe a decision
that was made and later undone — they are kept because the reversal is only half-done in
places (docs, env templates, naming), and knowing the original intent explains the
leftovers.

Numbering continues the ADR series in `.ai/decisions.md`; entries below either restate an
ADR with its current status or record something that happened after that file froze.

---

## Still in force

### D-001 · NestJS monorepo, two applications
Storefront API and Admin API are separate NestJS applications in one monorepo, sharing
three libraries. Rationale: different auth mechanisms, different rate limits, different
exposure — the admin API is meant to sit behind an internal boundary. Cost: two build
targets, two PM2 processes, and shared code has to go through `@app/*` libraries rather
than relative imports.

### D-002 · TypeORM with hand-written SQL migrations
`synchronize: false` everywhere. Schema changes are numbered `.sql` files in
`backend/migrations/`, applied by `backend/scripts/run-migrations.ts`, which creates a
`schema_migrations` table and applies only files not already recorded there.
TypeORM's own migration CLI is configured (`data-source.ts`) but is **not** the path in
use — the `.sql` runner is. Do not mix the two.

### D-003 · Prices as integer cents
Every monetary column is an integer number of cents. No floats anywhere in the money
path. Frontend divides by 100 at render time.

### D-004 · Multi-locale via JSONB columns
User-facing text is a JSONB object keyed `{ en, vi, de }` on the same row, rather than
translation tables. Cheap to add a locale; the cost is that every read needs an explicit
fallback (`x?.[locale] ?? x?.en ?? ''`) because a locale key may be missing.

### D-005 · Response envelope
Success responses are `{ success: true, data, meta? }` and errors are
`{ success: false, error: { code, message, details } }`, applied globally via
`TransformInterceptor` and `HttpExceptionFilter`. Both frontends are written against this
shape; changing it is a breaking change across three workspaces.

### D-006 · DTOs + class-validator, entities never leave the controller
Validation is decorator-driven on DTO classes, with a global `ValidationPipe` set to
`whitelist + forbidNonWhitelisted`. Consequence worth remembering: an unexpected field in
a request body is a **400**, not a silently-ignored extra. Adding a field to a client
means adding it to the DTO.

### D-007 · Order codes generated by the database
`MA-YYYYMMDD-NNNN`, produced by a Postgres trigger over `order_code_seq` (migration
`008`). Keeps codes unique and gap-free under concurrency without app-level locking.
Application code must not synthesise codes.

### D-008 · Guest carts keyed by session id
Anonymous users get a `session_id`-scoped cart; `OptionalUserAuthGuard` lets the cart
endpoints serve both authenticated and anonymous callers. `POST /api/v1/cart/merge`
folds the guest cart into the user cart at login and marks the session cart `converted`.
Cart items lock their unit price at add time so a mid-session price change doesn't move
what the customer was quoted.

### D-009 · S3-compatible object storage, no local file serving
MinIO locally and on the VPS, AWS S3 / Cloudflare R2 supported by the same code path
(`forcePathStyle: true`). No files are ever written to the app's local disk, which is
what makes the PM2 processes disposable.

### D-010 · Store storage keys, build URLs at response time — 2026-07-26 (`084f8e9`)
The database holds bare object keys (`products/123/img.jpg`); `StorageUrlInterceptor`
prefixes `STORAGE_PUBLIC_URL` on the way out. Motivation: migrations `036` had just had to
rewrite every stored URL when the storage host changed, and that is not a thing anyone
wants to do twice. With keys in the DB the storage domain is an env var.

The interceptor deliberately passes through values that already look like absolute URLs,
so legacy rows keep working.

**The invariant this rests on** (established 2026-07-26 while repairing migrations
`036`/`037`): the stored key is the **S3 key with no bucket segment**
(`products/<id>/<uuid>-<name>.jpg`), and `STORAGE_PUBLIC_URL` therefore **must include the
bucket** (`http://host:9000/uniform-store`, `https://storage.<domain>/uniform-store`).
Get this wrong in either direction and every image breaks — a bucket in both places
yields a doubled `/uniform-store/uniform-store/` path, a bucket in neither makes MinIO
read the first key segment as a bucket name and return `NoSuchBucket`.
`assets.key` is the reference for the correct key format. See bugs.md B-011.

### D-011 · Cache behind an interface, in-memory first
`cache.interface.ts` with an LRU `MemoryCacheService` in use and a `RedisCacheService`
written but not wired. Deliberate: avoid a Redis dependency until traffic justifies it,
while keeping the swap to a one-line provider change.

### D-012 · Rate limiting via @nestjs/throttler
Both apps register `ThrottlerModule.forRoot([{ ttl: 60000, limit: 60 }])`. Note this is
a flatter policy than the per-route tiers described in the older ADRs and in
`.env.example` (`AUTH_THROTTLE_LIMIT`, `SEARCH_THROTTLE_LIMIT`, `CART_THROTTLE_LIMIT`) —
those variables are documented but not currently consumed.

### D-013 · Separate identity systems for customers and admins
Different tables (`users` / `admin_users`), different JWT secrets, different TTLs
(30d vs 8h), different guards. The admin role ladder (`super_admin` > `admin` > `editor`
> `analyst`) applies only to the admin side. Unifying them would be a security-relevant
change and needs its own decision.

## Reversed

### D-014 · Supabase Auth for customers — **REVERSED 2026-07-25**
Originally customers authenticated through Supabase Auth (ADR-003), with no password
hashes stored locally. Replaced with custom JWT + bcrypt: `SupabaseAuthGuard` →
`UserAuthGuard`, `OptionalAuthGuard` → `OptionalUserAuthGuard`, `users.password_hash`
added by migration `031`, `@supabase/supabase-js` dropped, the `supabase` config
namespace deleted in favour of `userJwt`.

Leftovers to be aware of: `backend/.env.example` and the root `.env.example` still list
`SUPABASE_URL` / `SUPABASE_ANON_KEY` / `SUPABASE_SERVICE_ROLE_KEY`; `setup.md` still
mentions them as optional; `admin/next.config.ts` still allows `**.supabase.co` as a
remote image host. None of these are read by application code any more.

### D-015 · Supabase-hosted Postgres — **REVERSED 2026-07-17, partially**
The database moved to a Docker-hosted Postgres 16. The dual-mode connection code
(`DATABASE_URL` or discrete `DB_*` vars) survives and still works, so pointing at a
hosted Postgres is a config change. What was removed on 2026-07-26 (`4aacab9`) is the
*automatic* SSL inference — SSL used to switch on when the host matched `supabase.co` or
when `NODE_ENV=production`, which broke connections to the local VPS Postgres. Now SSL is
on only when `DB_SSL=true` is set explicitly.

### D-016 · Everything in Docker — **REVERSED**, now PM2 on the host
The original plan (ADR-019) was containerised stateless deployment, and
`docker-compose.yml` still describes it. Production instead runs the four Node processes
directly under PM2 and containerises only Postgres and MinIO
(`docker-compose.infra.yml`, ports bound to `127.0.0.1`). The GHCR image build/push
pipeline described in `.ai/memory.md` is likewise not what `.github/workflows/` does
today — CI type-checks, CD SSHes in and rebuilds from source.

### D-017 · REST-only API — **DEFERRED, GraphQL compat layer retained**
ADR-002 chose REST and planned to replace the frontend's Vendure GraphQL client. The
backend *is* REST internally, but the storefront was never migrated. Instead
`apps/storefront-api/src/shop-api/` accepts Vendure GraphQL at `POST /shop-api`, switches
on the operation name, and calls the same internal services, reshaping results to match
Vendure's response types (~44 operations).

Rationale: the storefront was a working Vendure-based build and rewriting its whole data
layer was more risk than writing one adapter. Consequences, which are the real cost:
every storefront-visible contract now exists twice (service + shaping code), the
storefront is littered with `vendure-*` naming that describes nothing real, and
`shop-api.service.ts` is a 1700-line switch. Retiring it is the largest single item on
the roadmap.

### D-018 · Backend tests gate CI — **REVERSED 2026-07-20** (`4d60311`)
CI originally ran `jest`. The job is now commented out in `.github/workflows/ci.yml`
because failing suites were blocking deploys. CI gates on `tsc --noEmit` only.
Related and worth knowing: the type-check steps previously ended in `|| true`, so CI was
green regardless of errors and CD deployed broken code — that was fixed at the same time.

## Conventions adopted after debugging incidents

### D-019 · Every entity column gets an explicit `{ name: 'snake_case' }`
Not a style preference. TypeORM does not infer snake_case from camelCase properties, and
omitting the name on `@Column` / `@CreateDateColumn` / `@UpdateDateColumn` /
`@DeleteDateColumn` produced a `Cannot read properties of undefined (reading
'databaseName')` deep inside the paginated query builder — a failure that pointed
nowhere near the actual cause. Cost two debugging sessions (article entities, 2026-07-18).

### D-020 · QueryBuilder ordering uses property paths, not column names
`orderBy('a.publishedAt')`, never `orderBy('a.published_at')`. Raw column names in
`orderBy` break when combined with `leftJoinAndSelect` + `skip`/`take`. Fixed repo-wide
in `657a6f3`.

### D-021 · `compression` is `require`d, not imported
`const compression = require('compression')` in both `main.ts` files, with an eslint
suppression. It is a CJS module and `import compression from 'compression'` yields
`compression.default is not a function` at runtime under the current TS/interop settings.

### D-022 · Config lookups are namespaced `app.*`
`app.config.ts` uses `registerAs('app', ...)`, so `configService.get('storage')` returns
`undefined` — it must be `configService.get('app.storage')`. Several guards and services
were silently getting `undefined` config before this was noticed (2026-07-17).

### D-023 · Webpack externals for TypeORM
`backend/webpack.config.js` externalises `@nestjs/typeorm` and `typeorm` to break a
circular bundle that crashed the built output. Required for `webpack: true` in
`nest-cli.json` to work; the Dockerfiles compile libs separately and copy them into
`node_modules/@app/*` for the same reason.

### D-025 · `@Res()` bypasses the interceptor pipeline — transform by hand there
Discovered 2026-07-26 when every storefront image 404'd at
`https://electroai.shop/products/unknown/<file>.jpg` — the site origin plus a raw storage
key, instead of the storage domain.

`ShopApiController` uses `@Res()` without `passthrough: true` and calls `res.json()`. In
NestJS that means the handler's return value never enters the interceptor pipeline, so
**no global interceptor runs**. For `TransformInterceptor` that is intended — `/shop-api`
must answer `{ data }`, not `{ success, data }`. For `StorageUrlInterceptor` it was not:
once migration `037` converted the database to bare keys, those keys went to the browser
untouched and resolved relative to the storefront origin.

The symptom was masked for as long as the database held absolute URLs, which is why the
bug and the migration surfaced together.

Resolution: `transformUrls()` is public on the interceptor and the controller calls it
explicitly before `res.json()`. `@Res({ passthrough: true })` is **not** an alternative —
it would restore `TransformInterceptor` and break the GraphQL contract.

Rule going forward: a controller that takes over the response owns every transformation
the pipeline would have done for it. There is currently exactly one such controller.

### D-024 · `skipMagicNumbersValidation` on upload file-type checks
NestJS 11's `FileTypeValidator` defaults to magic-number sniffing via the ESM `file-type`
package, which rejects small files with no fallback to mimetype matching. The uploads
controller sets `skipMagicNumbersValidation: true` and relies on content-type + extension
+ size checks instead.
